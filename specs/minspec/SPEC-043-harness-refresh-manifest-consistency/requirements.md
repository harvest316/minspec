# MinSpec — Harness-refresh manifest consistency (Requirements)

> Traces to **[#890](https://github.com/AIClarityAU/minspec/issues/890)** (surfaced by sealbox PR #21). Root-caused per **[DR-003 RCDD](../../../docs/decisions/DR-003.md)** — the fix is not the bad-state data edit (a hand-reconciled manifest) but the *mechanism* that produced the inconsistent manifest **plus** the missing write-time gate, per the constitution's [*"Don't hope an LLM will follow rules — enforce it via code"*](../../../.minspec/constitution.md#L17) invariant and [G-7 write-time enforcement](../../../.minspec/constitution.md#L45).

## One-Sentence Scope

Make the harness-refresh hash manifest (`.minspec/generated-hashes.json`) record, for every managed section, the hash of the **final bytes on disk after every write path has run** — not a pre-normalization template body, and not `mergeFile`'s intermediate return that a *later* post-merge injection then overwrites — and add a **fail-closed write-time self-check** that refuses to persist a manifest that disagrees with the files on disk, so a refresh can never again bump a section's recorded hash while the on-disk content is unchanged.

## Context

Root-caused against the code, with `file:line` evidence. There are **two** distinct producers of a lying manifest — the normalization transform gap (the originally-diagnosed one) *and* the post-merge AGENTS.md injection ordering hole (surfaced adversarially, the exact file sealbox #21 named). Both are addressed by one design move: **record the manifest from the final on-disk bytes, after all writes.**

- **The manifest hash is computed from the pre-normalization body; the file bytes are computed from a whole-file normalization — two different transforms.** `mergeFile` records each section's hash inline from the raw per-section body: `newHashes[heading] = hashSection(genSection.body)` ([merge-refresh.ts:197](../../../packages/minspec/src/lib/merge-refresh.ts#L197)), and symmetrically from `existingBody` in the "user-modified" and INV-2 branches ([:189](../../../packages/minspec/src/lib/merge-refresh.ts#L189), [:193](../../../packages/minspec/src/lib/merge-refresh.ts#L193)), the new-section branch ([:202](../../../packages/minspec/src/lib/merge-refresh.ts#L202)) and the preserve pass ([:217](../../../packages/minspec/src/lib/merge-refresh.ts#L217)). But the bytes that reach disk are produced by `sectionsToMarkdown(mergedSections)` ([:222](../../../packages/minspec/src/lib/merge-refresh.ts#L222)), which re-joins **all** sections and whole-file normalizes: `parts.join('\n').replace(/\n{3,}/g, '\n\n').trimEnd() + '\n'` ([:98](../../../packages/minspec/src/lib/merge-refresh.ts#L98)). `hashSection` only `.trim()`s ([:81](../../../packages/minspec/src/lib/merge-refresh.ts#L81)) — it trims the whole body's leading/trailing whitespace but does **not** collapse an **internal** `\n{3,}` run. So a section body carrying an **internal** `\n\n\n` (the one normalization-erasable delta the two transforms disagree on) is **stored one way in the file and hashed a different way in the manifest**. (A *trailing* blank line is **not** a reproduction: `hashSection`'s `.trim()` and `sectionsToMarkdown`'s `trimEnd`/`\n{3,}` collapse both erase it, so the two agree — see AC-1.)
- **AGENTS.md is mutated a second time, AFTER the manifest is saved — the self-check as first drafted could not see it.** `AGENTS.md`'s bundled template has **no** `## Spec Kit Slash Commands` heading ([template-registry.ts:119-167](../../../packages/minspec/src/lib/template-registry.ts#L119) — its headings are *For AI Coding Assistants / Specs Directory / Decision Records / Constitution / Task Classification Guide / Rules*). That section is injected by a **separate** mechanism, `generateSlashCommandShims` → `injectAgentsSlashSection` ([slash-commands.ts:310-331](../../../packages/minspec/src/lib/slash-commands.ts#L310), body built at [:235-259](../../../packages/minspec/src/lib/slash-commands.ts#L235)), which runs at the **end** of the write path — `refreshHarnessFiles` line [893](../../../packages/minspec/src/lib/scaffold.ts#L893), `generateHarnessFiles` line [808](../../../packages/minspec/src/lib/scaffold.ts#L808) — **after** `saveHashes` ([:866](../../../packages/minspec/src/lib/scaffold.ts#L866) / [:779](../../../packages/minspec/src/lib/scaffold.ts#L779)). On refresh, `mergeFile` sees the previously-injected `## Spec Kit Slash Commands` section as a user-added section (absent from the template) and records `newHashes['Spec Kit Slash Commands']` in the preserve pass; `saveHashes` freezes that; **then** `injectAgentsSlashSection` rewrites that same on-disk section. On any refresh carrying a slash-command **guidance** bump (the #534 vsix-bump class — the same trigger as #890), the section's on-disk bytes change *after* the manifest is frozen → INV-1 is literally false at end-of-refresh, and a self-check placed "before `saveHashes`" validates the **pre-injection** state and passes anyway. Worse: because `parseSections` splits only on `## `, the `<!-- minspec:slash-commands:start -->` marker is **absorbed into the tail of the preceding `## Rules` section** (the template's last heading), so `Rules`'s on-disk body differs between `mergeFile`'s `merged` and the post-injection file too — recording from `merged` alone (not final disk) would still mis-record `Rules`. **This is why the fix records from the final on-disk bytes after `generateSlashCommandShims`, not from `mergeFile`'s return.**
- **`refreshHarnessFiles` persists in-memory hashes verbatim, never re-derived from final disk.** It calls `mergeFile` ([scaffold.ts:852](../../../packages/minspec/src/lib/scaffold.ts#L852)), assigns `allHashes[relativePath] = newHashes` ([:854](../../../packages/minspec/src/lib/scaffold.ts#L854)), and `saveHashes` ([:866](../../../packages/minspec/src/lib/scaffold.ts#L866)) — with no assertion that any recorded hash matches the bytes finally on disk, and before the AGENTS.md injection at [:893](../../../packages/minspec/src/lib/scaffold.ts#L893). There is **no gate**.
- **A third recording path exists: `seedConstitution`.** After the merge loop, `seedConstitution` rewrites `constitution.md` and re-records its hashes via `buildSectionHashes(parseSections(merged))` ([scaffold.ts:56-72](../../../packages/minspec/src/lib/scaffold.ts#L56), called at [:774](../../../packages/minspec/src/lib/scaffold.ts#L774)/[:861](../../../packages/minspec/src/lib/scaffold.ts#L861)). `buildSectionHashes` is **last-occurrence-wins** ([merge-refresh.ts:104-110](../../../packages/minspec/src/lib/merge-refresh.ts#L104)); the shared helper this spec introduces is **first-occurrence-wins**. Consistent-by-construction for the common case, but a constitution with a duplicate `##` heading would make the last-wins record and a first-wins self-check disagree — a false abort — and FR-2's "one hashing path" guarantee would simply not be met. Recording from final disk through the one shared helper subsumes this path too.
- **The first-init path is consistent by accident, not construction.** `generateHarnessFiles` writes `content` and hashes `parseSections(content)` — the same bytes it wrote ([scaffold.ts:766-767](../../../packages/minspec/src/lib/scaffold.ts#L766)) — but via `buildSectionHashes` (last-wins), and it also injects the AGENTS.md slash section afterwards ([:808](../../../packages/minspec/src/lib/scaffold.ts#L808)). So init has the *same* AGENTS.md ordering hole as refresh. That the paths agree today is not enforced anywhere.
- **`template-baseline.json` is a *different* hash space and must stay one.** It hashes the raw, `{{placeholder}}`-bearing template ([template-registry.ts:290-291](../../../packages/minspec/src/lib/template-registry.ts#L290)); comparing it against rendered/merged hashes is exactly what produced the perpetual false-positive drift toast (#117, [merge-refresh.ts:255-283](../../../packages/minspec/src/lib/merge-refresh.ts#L255)). So this spec's consistency check is **manifest vs on-disk bytes**, never manifest vs template-baseline.

### RCDD (DR-003) — symptom · mechanism · missing gate

- **Symptom (bad state).** sealbox PR #21 (`chore: reconciled harness baseline after vsix template bump`) fails the independent reviewer: `.minspec/generated-hashes.json` bumps `AGENTS.md → Rules` `75f6014e → bb5b6cb5`, but AGENTS.md is byte-unchanged in the diff and `template-baseline.json` still records `75f6014e`. The manifest records a section hash for content that did not change — *"the harness changed"* is a lie.
- **Mechanism (what produced it).** Two coupled producers, both a *"recorded hash ≠ final on-disk bytes"* gap:
  - *(normalization)* On the first refresh after a vsix bump gives a template section an internal `\n{3,}` that normalizes back to the on-disk bytes (`R1 → R2`, `normalize(R2) == normalize(R1) ==` disk): the written file is unchanged, but `mergeFile` records `hashSection(R2)` (pre-normalization) — a value that moves with **no on-disk content change**.
  - *(injection ordering)* For AGENTS.md, the manifest is saved and then `injectAgentsSlashSection` rewrites the `## Spec Kit Slash Commands` region (and shifts the start marker inside `## Rules`) — so the recorded hash is stale the instant the injection runs.
- **Secondary symptom (freeze-out) is transient, not permanent — and is resolved in steady state by the same fix.** The normalization gap *also* mis-fires the merge **decision** `oldHash && existingHash !== oldHash` ([merge-refresh.ts:190](../../../packages/minspec/src/lib/merge-refresh.ts#L190)): on the **single** upgrade-boundary refresh, the on-disk manifest still holds a *pre-fix* stale `oldHash`, so a section whose disk bytes normalize-match but whose stale `oldHash` differs is misclassified as user-modified and a genuine template update to it is withheld **that one refresh**. Once this spec's recording writes the manifest from final disk, `oldHash == hashSection(disk)` for every unmodified section on every subsequent refresh, so the freeze-out cannot recur in steady state; the residual is a one-refresh self-heal at the upgrade boundary, bounded and tested (AC-6). FR-1 does **not** change the decision comparison (INV-5) — the freeze-out is bounded, not "fixed by FR-1"; see AC-6.
- **Missing gate.** Refresh has no write-time predicate asserting *every* `generated-hashes` entry equals the hash of the corresponding on-disk section **after the last write**, before it is persisted. A pure data reconcile of the manifest (the sealbox #21 hand-commit of a derived subset) is the classic DR-003 tell that a gate is missing — the derived-and-coupled harness output must be regenerated by the tool and *proven* consistent, never hand-edited (siblings #705/#706/#763/#760/#758; MEMORY: "Harness-refresh output is derived+coupled").

**Core gap (one sentence):** the manifest hash and the on-disk bytes are computed by different transforms *and* by write paths that run after the manifest is saved, and nothing ever checks they agree, so a refresh can bump a recorded hash for content that did not change — a never-wrong violation, because the manifest is a derived view of file-system truth that is allowed to lie.

## Design spine (never-wrong)

The manifest is a **derived view of file-system truth, never a prediction** (EPIC-002 principle). Correctness has two layers, and the order between them is load-bearing:

1. **Consistency by construction — hash the FINAL bytes on disk.** After *every* write path has run (`mergeFile`, `seedConstitution`, and `generateSlashCommandShims`'s AGENTS.md injection), re-read each managed section-merge file and record its section hashes through one shared helper — so the manifest equals disk by definition, no matter which mechanism last touched the file. This is strictly stronger than "hash what `mergeFile` returned": for AGENTS.md, `mergeFile`'s return is *not* the final on-disk state.
2. **Fail-closed enforcement (enforce, don't trust).** A deterministic write-time self-check re-reads the files and asserts that every hash in the **disk-derived recording** — the map MinSpec builds by hashing the final on-disk bytes of the tracked files it wrote this run — equals the hash of the on-disk section; on any mismatch it **refuses to persist** the manifest and surfaces an error. Layer 1 makes this green; layer 2 guarantees a future regression that records from memory again (or a hand-edited manifest, or a commit/CI-time check) fails closed instead of shipping a lying manifest. Since [DR-089](../../../docs/decisions/DR-089.md) the **persisted** manifest is that recording *plus* the authorship corrections, applied **after** the check because they are records of authorship rather than claims about disk — **FR-3b** defines the boundary exactly, and INV-3 enumerates what the check still rejects across it.

## Functional Requirements

- **FR-1 (hash the final on-disk bytes).** The manifest records each managed section's hash from the **final bytes on disk**, re-read after every write path in `generateHarnessFiles`/`refreshHarnessFiles` has completed — including `seedConstitution` and `generateSlashCommandShims` — through a single shared helper `sectionHashesFromMarkdown(content)` that `parseSections` + `hashSection`es each section body, preserving **first-occurrence-wins** duplicate-heading semantics ([merge-refresh.ts:216-218](../../../packages/minspec/src/lib/merge-refresh.ts#L216)). The per-branch inline `newHashes[...] = hashSection(...)` assignments in `mergeFile` and the `buildSectionHashes(parseSections(...))` recordings at the write sites are retired as the manifest's source of truth (`mergeFile` may still return `newHashes`, but the persisted manifest is derived from disk).
- **FR-2 (one hashing path for every write site).** Every recording site — `generateHarnessFiles` first-init ([scaffold.ts:766-767](../../../packages/minspec/src/lib/scaffold.ts#L766)), `refreshHarnessFiles` file-absent branch ([scaffold.ts:846-847](../../../packages/minspec/src/lib/scaffold.ts#L846)), `mergeFile`, and `seedConstitution` ([scaffold.ts:71](../../../packages/minspec/src/lib/scaffold.ts#L71)) — routes through the **same** first-occurrence-wins helper over the **final on-disk bytes**, so no two paths can hash a section differently. This closes the three-way asymmetry between `buildSectionHashes` (last-wins) and the new helper (first-wins).
- **FR-3 (fail-closed self-check).** A new deterministic function `verifyGeneratedHashesConsistent(rootDir, hashes)` re-reads each currently-tracked section-merge template file on disk and asserts that every section hash **in the map it is handed** equals `hashSection` of that section's on-disk body. The map it is handed is the **disk-derived recording**, never the map that is finally persisted: since [DR-089](../../../docs/decisions/DR-089.md) those two deliberately differ, and **FR-3b** defines the difference. It is called **after** all writes (including the AGENTS.md injection), **after** the disk-derived recording is built, and **before** both the FR-3b authorship corrections and `saveHashes`; on any violation the write path **aborts with a clear, actionable error and does not persist** `generated-hashes.json` (the prior, last-good manifest is left intact). **Missing/extra-entry semantics (FR-3a):** a recorded path whose file is **absent** on disk is **skipped, not a violation** (a legitimately-removed template must never brick a refresh); only paths in the current `TEMPLATE_OUTPUT_PATHS` set that are **present-but-mismatched** abort. Stale keys not in `TEMPLATE_OUTPUT_PATHS` are pruned from the manifest before persist so it cannot accumulate untracked entries. No network, no LLM.
- **FR-3b (authorship exemption — the disk-agreement check binds only claims *about disk*).** [DR-089](../../../docs/decisions/DR-089.md) makes the manifest a record of **authorship**: an entry means *"MinSpec rendered these bytes"*, and for a **preserved** section it deliberately records a template body that is **not** on disk, because that divergence is the evidence the next merge reads (DR-089 §1). Preserving a user's edits is the *normal* outcome of a refresh, so a check that asserted disk-agreement over the **persisted** map would abort almost every real refresh. The check therefore runs over the **disk-derived recording**, and the three authorship corrections are applied after it, on the way to `saveHashes`:

  | Correction | Granularity | Effect on the persisted entry | Why disk-agreement cannot apply |
  |---|---|---|---|
  | `ManifestAuthorship.withheld[relPath][heading]` | heading | records the hash of the **template body MinSpec rendered and declined to write** | those bytes are deliberately not on disk — the divergence *is* the evidence (DR-089 §1) |
  | `ManifestAuthorship.unauthoredSections[relPath]` | heading | the heading is **deleted** — no entry at all | MinSpec rendered no body for it, so there is nothing it may honestly compare or claim |
  | `ManifestAuthorship.unauthored[]` | file | the file's **prior** entry is carried forward verbatim; no new hash is recorded | the entry describes an **earlier** run's write, not this run's disk, and detecting later divergence is exactly what that baseline is for |

  **The discriminator, named precisely.** It is **not** a new field and **not** a flag an entry carries: it is the `ManifestAuthorship` argument to `recordVerifyAndSaveManifest` ([scaffold.ts:1080](../../../packages/minspec/src/lib/scaffold.ts#L1080)), composed by the caller from `MergeResult.withheldTemplateHashes` and `MergeResult.unauthoredHeadings` ([merge-refresh.ts:202](../../../packages/minspec/src/lib/merge-refresh.ts#L202)). An entry is subject to the disk-agreement check **iff** it is in the disk-derived recording — its file is in `TEMPLATE_OUTPUT_PATHS`, present on disk, and **not** in `authorship.unauthored`. The exemption is thus a property of *which map the predicate is handed*, decided by the run that did the writing, rather than something an entry can assert about itself. That is deliberate: a per-entry "trust me, I'm exempt" marker would be forgeable from inside the manifest, which is the precise failure DR-089's Context calls out — *"a poisoned manifest is indistinguishable from an honest one by inspecting its contents."*

  **Nothing is added to the persisted format.** `generated-hashes.json` stays `{ [filePath]: { [heading]: hash } }` plus the `__minspec__.hashVersion` stamp (DR-089 §3); no per-entry authorship marker is written, and this spec does not add one. The consequence is a **caller contract**, not a format change — see FR-5.

- **FR-4 (idempotent refresh — regression guard, refresh-vs-refresh).** Two **consecutive refreshes** with no template change and no user edit: the **second** rewrites no managed file and bumps **no** recorded hash — `generated-hashes.json` is byte-identical across the two. The compare is always **refresh-vs-refresh**, never init-vs-refresh: `generateHarnessFiles` writes the raw rendered template while refresh re-emits through `sectionsToMarkdown` (normalizing `\n{3,}`), so the **first** refresh after init is a legitimate *settling* refresh that may rewrite a file whose raw body carried an internal `\n\n\n` (OQ-4). The fixed point is reached at R2, and idempotence is asserted there. This is the direct #890 / sealbox #21 regression: "a no-content-change refresh must not bump any hash."
- **FR-5 (scope of the check — documented, not a gap).** The self-check covers the section-merge templates tracked in `generated-hashes.json` (CLAUDE.md, AGENTS.md, .cursorrules, constitution.md). Because AGENTS.md's manifest entry is now recorded from the **final** on-disk bytes (post-injection, FR-6), its embedded `minspec:slash-commands` marker region is covered and consistent — it is no longer a hole. The check deliberately does **not** cover the separate managed-region **marker files** (CI workflow, git hooks, `.claude/commands/*`, `.cursor/rules/*` — a different mechanism, governed by `checkManagedRegionMarkers` / #760, never entered into `generated-hashes.json`) or `template-baseline.json` (a different raw-template hash space; coupling them reintroduces #117's false-positive class). Stated so a reviewer does not read the exclusion as an omission. **Caller contract (FR-3b).** `verifyGeneratedHashesConsistent` is a predicate over the map its caller supplies, so a consumer that hands it the **persisted** manifest without that run's `ManifestAuthorship` will report every preserved section as an inconsistency. That is the offline check's obligation, and DR-089 records it as a consequence: such a check *"must be given the same authorship information, or it will report every preserved section as an inconsistency"* ([#760](https://github.com/AIClarityAU/minspec/issues/760)).
- **FR-6 (AGENTS.md post-merge injection ordering).** Because `generateSlashCommandShims` injects/rewrites AGENTS.md's `## Spec Kit Slash Commands` marker region **after** the merge loop (and shifts the `<!-- minspec:slash-commands:start -->` marker into the preceding `## Rules` section body), AGENTS.md's manifest entry MUST be recorded — and the FR-3 self-check MUST run — **after** `generateSlashCommandShims` has finished, from the final on-disk bytes. `saveHashes` is the **last** manifest operation in both write paths, sequenced after `generateSlashCommandShims`. Consequence to test: after a refresh that changes slash-command **guidance**, `generated-hashes.json['AGENTS.md']` equals `sectionHashesFromMarkdown` of the post-injection on-disk AGENTS.md, and `verifyGeneratedHashesConsistent` returns `[]` against final disk (AC-7).

## Invariants

- **INV-1 (the manifest records MinSpec's own output).** Every hash in `generated-hashes.json` that MinSpec records **for bytes it rendered** equals `hashSection` of that section's body **as it exists in the file on disk after the last write of the run**. **Narrowed by [DR-089] (#1697) - pending that DR's acceptance, `status: proposed` as of this edit:** a section the merge *preserved* records the hash of the **template body MinSpec declined to write**, which is deliberately not on disk - that divergence is the evidence the next refresh reads. The consistency tripwire still runs against the disk-derived map, before the authorship corrections are applied, so it keeps its original strength — specified as **FR-3b**, which names the discriminator and enumerates what INV-3 still rejects across it.
- **INV-2 (idempotent refresh).** Two consecutive refreshes with no template change and no user edit reach a fixed point at the **second**: byte-identical harness files **and** a byte-identical `generated-hashes.json`. Re-running refresh from the settled state bumps zero hashes. (The first refresh after init may settle a raw-template `\n{3,}` — OQ-4.)
- **INV-3 (fail-closed).** If any manifest entry **that asserts MinSpec's authorship of the current on-disk bytes** disagrees with disk, the generate/refresh path **refuses to persist** `generated-hashes.json` and surfaces an error — it never ships an inconsistent manifest. (Enforce, don't trust — constitution [L17](../../../.minspec/constitution.md#L17).) **Narrowed by [DR-089](../../../docs/decisions/DR-089.md) (#1697) — pending that DR's acceptance, `status: proposed` as of this edit:** the narrowing is to *which entries make that assertion* (FR-3b). It is **not** a narrowing of the assertion's strength, and the qualifier is load-bearing in one direction only — an entry that does claim current disk is judged exactly as before.

  **What INV-3 still rejects after the FR-3b carve.** Stated explicitly, because an exception that swallowed its own rule would be a worse defect than the contradiction it resolves:

  1. **Every entry in the disk-derived recording** — the whole of what MinSpec claims it wrote this run — must equal `sectionHashesFromMarkdown` of that file's final on-disk bytes, and it is checked **in full, before any correction is applied**. The corrections then act on that already-verified set in exactly two ways: a `withheld` heading's hash is **replaced** (by the template body MinSpec declined to write), and an `unauthoredSections` heading is **deleted**. So the persisted map does deliberately carry hashes that are not claims about disk — that is DR-089 §1, not a gap — but each one replaces a heading the check had already confirmed present on disk. No correction can introduce a heading, a file, or a hash for a section this run never examined (point 4).
  2. **A recorded section missing from an otherwise-present tracked file is still a violation**, not a skip — claiming a hash for content that is not on disk is the exact class of lie the gate exists to catch. Only a wholly **absent file** is skipped (FR-3a).
  3. **A record-before-write regression still fails closed.** If a future change records the manifest from memory, or before a later mutator (`seedConstitution`, the AGENTS.md slash injection) has run, the recorded set diverges from final disk and the refresh aborts without persisting — R4's mitigation is unchanged, and this is the tripwire's whole purpose.
  4. **The corrections cannot widen themselves.** They are keyed by heading *within* an already-checked file entry, so none can introduce a file key outside `TEMPLATE_OUTPUT_PATHS`, and `applyAuthorshipCorrections` overrides a heading **only when that heading is already in the disk-derived map** — a withheld hash for a heading disk does not carry is dropped rather than invented ([scaffold.ts:1177](../../../packages/minspec/src/lib/scaffold.ts#L1177); pinned by `scaffold.test.ts`). *Known residual:* that guard uses `in`, which walks the prototype chain, so the eight `Object.prototype` names are a latent exception — filed as [#1752](https://github.com/AIClarityAU/minspec/issues/1752), latent rather than live because MinSpec ships no template heading with a prototype name.
  5. **A carried-forward entry is admitted only on proof.** The prior entry for an `unauthored` file is read through `loadProvenHashes` ([merge-refresh.ts:1294](../../../packages/minspec/src/lib/merge-refresh.ts#L1294)), whose `proven` set is **empty** unless the manifest carries `__minspec__.hashVersion === MANIFEST_HASH_VERSION`; an absent, older or unrecognised stamp yields no carried-forward entries at all (DR-089 §3). The exemption from disk-agreement is therefore paid for by a stricter admission test, not by an absence of one.

  What INV-3 must **not** reject is a preserved section's withheld-template hash differing from disk. That divergence is not an inconsistency — it is the evidence DR-089 §1 requires, and asserting disk-agreement over it would abort the refresh on the ordinary outcome of preserving a user's edits.

- **INV-4 (deterministic, Tier-0, offline, byte-stable serialization).** All hashing and verification is pure filesystem + SHA-256; no network and no LLM are reachable from the record/verify path. Same inputs → same manifest **byte-for-byte**: the manifest is serialized (`JSON.stringify(hashes, null, 2)`) with **deterministic key ordering** — file keys in `TEMPLATE_OUTPUT_PATHS`/`TEMPLATE_NAMES` iteration order, section keys in `parseSections` document order — so "byte-identical" (INV-2) is a property of the serializer, not an accident of insertion order (constitution invariant #1: core works offline).
- **INV-5 (merge decision unchanged) - SUPERSEDED by [DR-089] (#1697) - pending that DR's acceptance, `status: proposed` as of this edit.** As written for SPEC-043 this held: the fix changed only how hashes were **recorded**, never which section body `mergeFile` **keeps**. #1697 established that *which body is kept* was itself the defect - a missing baseline was read as proof of no change, and the template body overwrote the user's, exactly as `mergeFile` still does today (verified: [merge-refresh.ts:222-228](../../../packages/minspec/src/lib/merge-refresh.ts#L222) - `else if (oldHash && existingHash !== oldHash)` falls through to the template-body branch whenever `oldHash` is absent). DR-089 §1-§3 **propose** making `mergeFile` fail closed on absent evidence instead of overwriting; that change is not yet implemented, so this invariant's decision has not changed in code - only a proposal to change it exists. The original sentence read: User-edit preservation (#153 duplicate-heading handling, #706 authored-list-items guard) is behaviourally identical; existing merge-refresh tests stay green. (The bounded upgrade-boundary freeze-out of AC-6 is a *pre-existing* consequence of the stale on-disk manifest, not a decision change introduced here.)

## Vertical slices (thinnest-first; ordering is load-bearing)

1. **Slice 1 — consistency by construction (FR-1, FR-2, FR-4, FR-6).** Add `sectionHashesFromMarkdown`. Files: `merge-refresh.ts`, `scaffold.ts` (incl. `seedConstitution`). Ships with the T0 INV-1/INV-2 tests and the T3 sealbox-#21 + AGENTS.md-guidance-bump regressions.

## Open Questions

- **OQ-1 (gate posture: throw vs soft-skip).** Should `verifyGeneratedHashesConsistent` **throw** (abort the whole refresh) or return violations for a warn-and-skip-persist? *Proposed:* **throw** — a lying manifest is never-wrong-critical; `initRefreshCommand` already wraps `refreshHarnessFiles` in a try/catch that renders a clear error ([init.ts:933-942](../../../packages/minspec/src/commands/init.ts#L933)); aborting persists nothing and leaves the last-good manifest intact. Resolve in Clarify.
- **OQ-2 (pre-tracked machine-local state).** Should this spec also untrack already-committed `generated-hashes.json`/`template-baseline.json`? *Proposed:* **out of scope** — filed as [#924](https://github.com/AIClarityAU/minspec/issues/924); consistency is orthogonal to tracking. Resolve in Clarify.
- **OQ-3 (also cross-check template-baseline?).** *Proposed:* **no** — different hash space; equal only incidentally for placeholder-free sections; coupling reintroduces #117. Resolve in Clarify.
- **OQ-4 (normalize init output so init→refresh is a fixed point?).** `generateHarnessFiles` writes the raw rendered template; `refreshHarnessFiles` re-emits through `sectionsToMarkdown`, which collapses `\n{3,}`. So the first refresh after init can legitimately rewrite a file (and settle its hash) even with no template change — meaning INV-2's fixed point holds from **R2**, not from init. *Proposed:* **do not normalize at init** — keep init emitting the raw template (avoids churning exact-byte init tests and a visible harness-byte change), treat the first refresh as an expected settling pass, and specify every idempotence assertion as **refresh-vs-refresh** (AC-2, AC-6). Resolve in Clarify.

## Clarify

*Resolutions drafted by Claude (agent) 2026-07-25 as engineering defaults, per the maintainer's "you draft" instruction. Each is the proposed default from Open Questions, chosen with rationale. **These are confirm-or-redirect drafts — the human ratifies them at Approve Spec** (the hash-lock gate); nothing here is a human sign-off.*

- **OQ-1 — gate posture → RESOLVED: throw (abort-without-persist).**
  A manifest that disagrees with disk is the exact never-wrong failure this spec exists to prevent, so the fail-closed action is to stop, not to warn-and-continue. The command path already surfaces a thrown refresh error cleanly ([init.ts:933-942](../../../packages/minspec/src/commands/init.ts#L933)) and, because the abort happens *before* `saveHashes`, the previous good manifest is untouched — the user re-runs Refresh (the same "regenerate via the ext, never hand-fix a subset" remedy #890 prescribes) and it succeeds once Slice 1 is in. A soft skip would let an inconsistent in-memory set be re-surfaced as "nothing wrong," defeating the point.

- **OQ-2 — pre-tracked machine-local state → RESOLVED: out of scope; filed as [#924](https://github.com/AIClarityAU/minspec/issues/924).**
  Untracking already-committed ephemeral state is a distinct change with its own blast radius (a `git rm --cached` + commit across existing projects) and does not affect whether the manifest is internally consistent — which is what makes sealbox #21 fail review and what this spec fixes. Keeping it out holds SPEC-043 at a tight T3. Per the DR-023 forward rule, the follow-up is materialized as a filed issue (#924), not left as prose.

- **OQ-3 — cross-check template-baseline → RESOLVED: no.**
  `template-baseline.json` hashes the raw, `{{placeholder}}`-bearing template ([template-registry.ts:290-291](../../../packages/minspec/src/lib/template-registry.ts#L290)); the rendered/merged manifest hashes rendered content. They are equal only incidentally, for a placeholder-free section. Asserting equality between them is precisely the #117 false-positive drift class ([merge-refresh.ts:255-283](../../../packages/minspec/src/lib/merge-refresh.ts#L255)). The check stays **manifest vs on-disk bytes**.

- **OQ-4 — normalize init output → RESOLVED: no; first refresh settles; assert idempotence refresh-vs-refresh.**
  Making `generateHarnessFiles` emit `sectionsToMarkdown`-normalized bytes would make init itself a fixed point, but it would change the exact bytes init writes (churning `scaffold.test.ts`'s init assertions) for a wart that a single refresh already settles. The tighter, lower-blast-radius resolution is to keep init raw and encode the sequencing into the tests: every idempotence assertion compares the **second** of two refreshes, never init-vs-refresh. This is a closed decision, not a deferral — no follow-up issue is warranted.

No Clarify resolution blocks the Plan phase; all four resolve to a stated default. OQ-2's materialized follow-up is [#924](https://github.com/AIClarityAU/minspec/issues/924).

## Acceptance Criteria

- **AC-1 (FR-1, INV-1) — the load-bearing reproduction is an INTERNAL `\n\n\n`.** After a refresh where a template section body acquires an **internal** `\n\n\n` run that `sectionsToMarkdown` collapses back to the on-disk bytes (so disk is byte-unchanged), the recorded hash for that section equals `hashSection` of the on-disk body, and the harness file is byte-unchanged. **This fixture must FAIL on pre-fix code (red-before-green)** — pre-fix records `hashSection(pre-normalization body)` and bumps the hash. A *trailing* blank line is included **only** as a "must-also-stay-consistent" assertion explicitly labeled **not the reproduction** (both transforms erase it, so it never diverges).
- **AC-2 (INV-2, FR-4) — refresh-vs-refresh.** Scaffold, run one **settling** refresh (R1), then a second refresh (R2) with no template change and no user edit: R2 rewrites no managed file and produces a `generated-hashes.json` byte-identical to R1's (zero hash bumps). The assertion is R2==R1, never init==refresh.
- **AC-3 (FR-3, INV-3).** With a deliberately-inconsistent hash injected into the **disk-derived recording** in memory before persist (the map the check is handed — where a record-before-write regression would manifest), `verifyGeneratedHashesConsistent` aborts the write path; `generated-hashes.json` on disk is **not** overwritten with the inconsistent set (last-good preserved); the failure is surfaced. On the fixed (Slice 1) path the check passes.
- **AC-4 (INV-5, INV-1) — preservation, and what the manifest records for it.** A user-modified section is still preserved verbatim after refresh (existing #153 / #706 merge tests remain green). **Revised by [DR-089](../../../docs/decisions/DR-089.md) (#1697) — pending that DR's acceptance:** the second clause as originally written — *"and its recorded hash equals `hashSection` of its on-disk body"* — is precisely the claim DR-089 reverses, and asserting it would re-forge the permission slip #1697 was filed over. What is recorded now depends on which preservation occurred: a section the **template also carries**, whose body MinSpec rendered and declined to write, records the **withheld template hash** (≠ its on-disk hash); a **user-added** section the template does not carry records **nothing at all** (`MergeResult.unauthoredHeadings`). Neither is an INV-3 violation — see FR-3b.
- **AC-5 (INV-4) — determinism + byte-stable serialization.** No network / LLM call is reachable from the record or verify path; the manifest is **byte-identical** across N runs on a fixed fixture, including stable file/section key ordering in the serialized JSON.
- **AC-6 (INV-5, freeze-out bound).** Starting from a *pre-fix* on-disk manifest whose `oldHash` for a section is the stale pre-normalization value, a refresh whose V2 template makes a genuine content change to that section may withhold the update on the **first** (upgrade-boundary) refresh; the withheld template update **lands on the second refresh**, and no further refresh withholds it. (Bounds the transient rather than claiming FR-1 eliminates it.)
- **AC-7 (FR-6) — AGENTS.md post-merge injection.** After a refresh that changes slash-command **guidance** (a `COMMAND_GUIDANCE` bump), `generated-hashes.json['AGENTS.md']` equals `sectionHashesFromMarkdown` of the **post-injection** on-disk AGENTS.md (both the `## Spec Kit Slash Commands` section and the start-marker-absorbing `## Rules` section), and `verifyGeneratedHashesConsistent` returns `[]` against final disk. **This fixture must FAIL on a variant that records from `mergeFile`'s `merged` / saves before injection** (red-before-green for FR-6).
- **AC-8 (FR-3a).** A `generated-hashes.json` carrying an entry for a path with **no** on-disk file (a removed/renamed template, or a hand-edited manifest) does **not** abort refresh — the absent entry is skipped and pruned; only a present-but-mismatched entry aborts.
- **AC-9 (FR-3b, INV-3) — preserving a user's edits must not abort the refresh.** A refresh that preserves user content completes and **persists**: the self-check returns `[]` against the disk-derived recording, `saveHashes` runs, and the persisted manifest carries the withheld template hash for a **held** section (≠ its on-disk hash) and **no** entry for a **user-added** section. **This fixture must FAIL on a variant that runs the self-check over the corrected/persisted map** — that variant is the pre-carve reading of FR-3/INV-3, and it aborts on every refresh that preserved anything (red-before-green for FR-3b). *Coverage today:* the **user-added** half is already pinned end-to-end against a real `refreshHarnessFiles` by `merge-refresh.test.ts` AC-63, which is only green because the product already behaves as FR-3b now specifies; the **withheld** half is pinned at the unit level (`mergeFile`'s `withheldTemplateHashes`, `applyAuthorshipCorrections`) but **not yet** end-to-end through the persisted manifest — tracked as [#1785](https://github.com/AIClarityAU/minspec/issues/1785).

## Risks

| # | Risk | Mitigation |
|---|------|-----------|
| R1 | **Gate fires on a legitimately-inconsistent legacy manifest** on the first post-upgrade refresh, aborting the refresh. | This is the point (fail-closed), and it is self-healing: Slice 1's final-disk recording runs *before* the gate in the same refresh, rewriting the manifest consistently — so the gate sees the freshly-consistent set and passes. A pre-existing hand-broken manifest is fixed by the very refresh that would trip the gate. The **only** residual is the AC-6 one-refresh freeze-out of a genuine template update at the upgrade boundary (self-heals on the next refresh). |
| R2 | **Slice mis-order.** Landing the gate (Slice 2) before the fix (Slice 1) fails closed on the existing bug on every refresh. | Encoded as a sequencing invariant in the plan: Slice 1 first. |
| R3 | **Duplicate-heading hash semantics drift** — the shared helper must keep first-occurrence-wins, or a doc with repeated `##` headings changes which body is recorded, and the last-wins `buildSectionHashes`/`seedConstitution` paths would disagree with the first-wins self-check (false abort). | `sectionHashesFromMarkdown` mirrors the existing first-occurrence rule ([merge-refresh.ts:216-218](../../../packages/minspec/src/lib/merge-refresh.ts#L216)); recording from final disk through this **one** helper retires the last-wins paths; a T1 test pins duplicate-heading behaviour on both a `mergeFile`-produced and an `:847`/init-produced file. |
| R4 | **Post-merge mutators bypass the manifest.** AGENTS.md is rewritten by `generateSlashCommandShims` after the merge loop; a future post-merge mutator of a tracked file would re-open the gap if recording ran before it. | Recording is done from a **final disk re-read after all writes**, and `saveHashes` is the last manifest op (FR-6). Any future recording-before-write regression is caught by the FR-3 gate (recorded-from-memory ≠ disk). |
