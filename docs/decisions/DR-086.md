# DR-086: Autonomy is a second axis, bounded by an enumerated stop list

> **Born `proposed` per DR-029** - acceptance is a separate human act
> (*MinSpec: Accept ADR*). This record's live status is its frontmatter `status:`
> field, not this note.

## In plain terms - what this changes for you

Today every turn ends with a list of recommended next actions and you reply "do
recs". This says: let the agent just do them, and interrupt you only for things
on a **written list** of what it may never decide alone.

The list is the whole point. "Stop when you are seriously stuck" cannot be the
rule, because the agent is the one judging whether it is stuck - and a gate that
certifies itself is the thing this project already refuses everywhere else.

## Context

DR-076 cut the gates that existed for multi-human trust. This is a different
cut. The human is still the only human; what is being removed is a
**conversational round-trip inside one person's own session**.

The round-trip currently carries no information. The agent computes a
recommendation with its reasons and costs; the human replies with unconditional
assent. Nothing is decided at that step - it is a confirmation of an analysis
that already happened, and the founder's own framing is that it is time spent
rubber-stamping, the same complaint that produced DR-075/DR-076.

The target user is someone who wants to work **at the level of SPECs and DRs**
and not below it. That is precisely the customer DR-075 names.

### Why this is more dangerous than a permissions bypass

The founder called it *"like CC's bypass permissions but worse"*, and that is
exactly right for a reason worth stating: a permissions bypass removes a
**confirmation** on an action the human already chose. This removes the
**choice**. The agent picks, and the alternatives it rejected are never seen.

This is not hypothetical. In a single working session (2026-08-19/20) two
recommendations were refuted by evidence the agent gathered **after** making
them:

1. **PR #1215** was recommended for "the residual is small, re-implement on
   main". Running the PR's own test file against `main` then showed **26 of 29
   failing** - the residual was large, and the recommendation reversed.
2. **A SPEC id** was allocated as free after reading `max(existing)` from a
   stale `origin/main` ref. It was not free; the duplicate reached `main` and
   needed a repair PR (#1574).

Under naive auto-proceed both execute before the correcting evidence arrives.
The lesson is not "do not proceed" - it is that **when** a recommendation may be
executed matters as much as whether.

### Why it is not #183 and not solo mode

- **#183** (gate-placement) asks *where* the human gate sits. This asks whether
  the human is consulted at all on a choice already analysed. A repo can answer
  these two independently.
- **#1169 / SPEC-065** cuts gates for multi-human trust. This cuts a
  conversational step for a single human. SPEC-065 could ship complete and this
  would still be open.

## Decision

### 1. Autonomy is a second axis, not a new mechanism

`mode: solo | team` answers *whose consent is required*. A separate
`autonomy: ask | act` answers *is the human consulted on a choice the agent has
already analysed*. The two are orthogonal and both are configuration
(SPEC-065 FR-1's single-resolver rule applies unchanged). Default is `ask`.

### 2. The stop condition is an enumerated list, never the agent's judgement

Under `autonomy: act` the agent proceeds on its own recommendation **except**
for these classes, which always stop and ask:

1. **Irreversible or outward-facing acts** - publish, repo visibility, deletion,
   anything leaving the machine (DR-076 keep; constitution-level).
2. **T3/T4 spec approval and DR acceptance** - the read-before-build moments
   (DR-076 keep, DR-029, DR-056).
3. **Spend** above a configured threshold, including paid-model failover.
4. **Evidence-incomplete recommendations** - see §3.
5. **Genuine ties** - where the agent has no recommendation, or two options are
   materially equivalent. A forced pick here manufactures a decision that was
   never made.
6. **Anything that would edit this list**, or the autonomy setting itself.

"Seriously stuck" is deliberately **not** on the list. It is unenumerable and
self-judged; a stop rule the agent evaluates about its own competence is the
same self-certification defect the machinery merge gate exists to prevent
(#509). If a new stop class is discovered, it is added here by amendment.

### 3. The evidence-freshness rule

A recommendation MUST NOT be auto-executed while the task is still gathering
evidence that could refute it. Concretely: if the agent's plan includes further
verification of the premise the recommendation rests on, the recommendation is
**provisional** and does not qualify for `act` until that verification lands.

This is the rule the two refutations above would have needed. It is stated as a
sequencing constraint, not as a confidence judgement, so it can be checked.

### 4. Rejected alternatives must be recorded

Under `act`, the agent MUST write down the options it rejected and why, in the
durable artifact (PR body, issue comment, DR), not only the option it chose. The
human is no longer seeing them live, so the record becomes the only way the
decision can be reviewed afterwards. An `act`-mode action with no stated
alternatives is a defect, not a terse success.

### 5. Blast radius unchanged

This governs **this repo's own workflow**. Shipping an autonomy level to
adopters is a separate decision: an agent acting unattended in someone else's
repo is a far larger claim than one scoped here (constitution invariant 3).

## Consequences

- The rubber-stamp round-trip disappears for the large class of decisions that
  are already analysed, costed, and reversible.
- **Accepted risk:** a wrong recommendation now executes. The mitigations are
  the enumerated stop list, the evidence-freshness rule, and the fact that the
  classes with real blast radius are exactly the ones excluded.
- The audit burden moves from the human's attention to the agent's writing.
  §4 is load-bearing, not decorative - without it the mode trades a visible
  decision for an invisible one.
- The stop list will be found incomplete. That is expected and is why it is a
  written artifact under amendment rather than a disposition.

## Amendment A (2026-09-05) - PROPOSED, not accepted

**Records the moment `act` was authorized for this repository, which DR-086 itself
deliberately left open.** The original record defines the axis and its `ask` default; it
never said when the default would change. This amendment supplies that, because §2.6
makes editing the autonomy setting a mandatory stop-and-ask class and §4 obliges an
act-mode decision to record its rejected alternatives in a durable artifact. A bare
one-line config flip carrying neither is exactly the invisible decision §4 exists to
prevent, and the review panel blocked #1743 on that ground before this section existed.
Held until the founder ratifies it under their own account: the merge keystroke on the
PR carrying this amendment is theirs, and the App is not a bypass actor on the ruleset,
so that is enforced by config rather than by convention. Triggered by [minspec #1743].

### The decision

`.minspec/config.json` gains `"autonomy": "act"`, for **AIClarityAU/minspec only**.

### The authorization

The founder (`harvest316`, this repository's sole owner) authorized it on 2026-09-05,
in these words:

> now that the MinSpec specs are basically complete, the direction is set. i don't need
> to know the implementation details. i trust that the ai-review and other quality
> measures we have in place are sufficient.

Recorded verbatim by the chief-of-staff session asked to write it down. The record is
not the act.

### Rejected alternatives (§4)

- **Stay on `ask`.** Rejected. The specs are substantially complete, so a per-item
  round-trip now buys review of implementation detail the founder has said they do not
  need to see. The round-trip's cost is no longer paid for by what it returns.
- **Flip `act` and relax the stop list with it.** Rejected. The six classes in §2 are
  what make `act` grantable at all, and this change leaves every one intact. Class 6 in
  particular still means a future edit to this same setting stops and asks - which is
  why this amendment exists rather than the value simply appearing.
- **Grant `act` across every MinSpec-managed repository.** Rejected, and moot on the
  evidence: of the 17 repositories on this machine carrying `.minspec/config.json`,
  MinSpecPro is the only one holding `scripts/lib/autonomy.ts`,
  `scripts/dispatch-issue.sh` or `scripts/drain-inbox.sh`. The key has no consumer
  anywhere else, so writing it there would be an inert signpost - the failure mode a
  never-wrong product cannot afford. Per-repo scoping is constitution invariant 3
  working as designed, not a limitation to route around.

### What this does not change

`act` widens what the two unattended merge actors may do without asking, and nothing
else. `scripts/lib/autonomy.ts` still denies any diff touching `scripts/lib/autonomy.*`
or `.minspec/config.json` even under `act`; an unrunnable gate still denies; an empty
stop-class list denies rather than admits. `--admin` remains human-only and no failing
check may be bypassed. The enumerated list in §2 is unamended here.

### Known gap at the time of writing

`autonomy` is read by `scripts/lib/autonomy.ts` but is absent from the extension's
`MinspecConfig` and `DEFAULT_CONFIG` (`packages/minspec/src/lib/config.ts:43-73`), so
the setting is unvalidated and invisible to the product surface. Tracked as
[minspec #1795], deliberately not fixed in the PR carrying this amendment.
