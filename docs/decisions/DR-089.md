# DR-089: The harness manifest records authorship, not disk

> **Born `proposed` per DR-029** - acceptance is a separate human act
> (*MinSpec: Accept ADR*). This record's live status is its frontmatter `status:`
> field, not this note.

## Context

`.minspec/generated-hashes.json` decides, on every *Refresh Harness Files*, whether a
section of a managed file is MinSpec's own output (safe to update from the template) or
the project's content (must be preserved). #1697 established that it was answering that
question wrongly in two independent ways, and that the wrong answer deleted a Principle's
standing exception - a paragraph that authorised shipped code - from a live project.

1. **A missing hash was read as proof of absence of change.** `mergeFile` treated "no
   recorded hash for this heading" as "unmodified" and wrote the template body over the
   user's. The manifest is gitignored machine-local state, so it is absent on every fresh
   clone, worktree and CI checkout - which is why the loss recurred on three branches.
2. **A present hash could be a forgery.** Both recording sites hashed whatever was on
   disk, so the user's own paragraph was recorded as MinSpec's output. A baseline that
   *was* present was therefore not evidence of anything.

The second is the one that matters for this record, because it is not fixable by reading
more carefully: **a poisoned manifest is indistinguishable from an honest one by
inspecting its contents.** Every entry is a well-formed hash of a real section. Nothing
in the file says which entries were claims MinSpec was entitled to make.

## Decision

### 1. The manifest records authorship, which is not the same as recording disk

A hash in the manifest means *"MinSpec rendered these bytes"*, not *"these bytes are on
disk"*. Concretely:

- A section the merge **preserved** records the hash of the **template body MinSpec
  declined to write** - bytes that are deliberately not on disk. The next refresh then
  sees `oldHash != existingHash`, which is genuine positive evidence that the user's
  content diverges, so the section is preserved *on evidence* rather than on absence, and
  the report falls silent after one refresh instead of nagging forever.
- A file `generateHarnessFiles` **skipped** because it already existed yields no new
  claim; its prior entry is carried forward unchanged rather than erased, because
  the manifest is rebuilt from scratch each run and omitting a file destroys a claim an
  earlier run legitimately made.

### 2. Missing evidence fails closed

No recorded hash means no evidence, so the existing body is preserved and the hold is
reported. Absence of evidence is not evidence of absence, and the fail-open direction was
the one that destroyed data.

### 3. The manifest carries a format version, and an unrecognised one is distrusted

`__minspec__: { hashVersion }`. When the stamp is absent, older, or unreadable, **every**
entry is refused at the loader rather than at each decision site - so a site nobody
enumerated still fails closed. Comparison is `===`: a *newer* stamp is distrusted too,
because a build that cannot understand the format cannot judge which of its claims are
honest.

This is the part that cannot be undone. The stamp ships into every adopter's `.minspec/`
directory, and a later format change has to decide explicitly what to do with v2 files.

### 4. This narrows SPEC-043's INV-1 and supersedes its INV-5

Stated plainly rather than left to source comments:

- **INV-1** ("the manifest never records a hash for bytes that are not on disk") is
  **narrowed**. It now binds only hashes MinSpec records for *its own output*. A withheld
  template body is recorded precisely because it is not on disk - that is the signal.
- **INV-5** ("changes only how hashes are recorded, never which section body `mergeFile`
  keeps") is **superseded**. Which body is kept is exactly what #1697 had to change.

SPEC-043's consistency tripwire keeps its original strength: it still runs against the
disk-derived map, before the authorship corrections are applied.

## Consequences

**Accepted cost.** A template improvement no longer lands on a section the user has
modified, and the user is told once. That is what "preserve your edits" has to mean, but
it does mean a project that wants the new template text applies it by hand.

**A future offline manifest check cannot assume the file mirrors disk** (#760). It must be
given the same authorship information, or it will report every preserved section as an
inconsistency.

**Rollback is designed to be safe, but this is not yet verified** - the `hashVersion`
format does not exist in code yet (grep: no `__minspec__`/`hashVersion` hit in
`merge-refresh.ts` or any src/test), so there is nothing to test against. The intended
behavior: older code meets a v2 manifest, does not crash, does not treat the stamp as a
file path, and drops it on its next write. Re-upgrading costs one further one-time
notice. This needs a real test once §1-§3 are implemented, before the claim can be
upgraded to "tested".

## Alternatives rejected

- **Commit the manifest.** Makes the baseline travel, and puts a generated file that
  changes on every refresh into version control, where it conflicts on any branch that
  also refreshed.
- **Derive the baseline from git history.** Needs a trustworthy marker for MinSpec's last
  write; commit-subject matching breaks on squash merges and amended messages, and it
  fails outright on a shallow clone.
- **Record nothing for a preserved section.** Fixes the loss equally well, but the notice
  then fires on every refresh forever with no dismissal path - alert fatigue, which is the
  "no silent gate" failure wearing different clothes.
