# DR-090: The triage dispute lane

> **Born `proposed` per DR-029** — acceptance is a separate human act
> (*MinSpec: Accept ADR*). This record's live status is its frontmatter `status:`
> field, not this note. The mechanism is specified in SPEC-066; what acceptance
> settles is the **policy** in §2, §4 and §6.

## Context

DR-072 gave a triage-held issue a human exit, but only for the tier hold: human_only is
a content class, so no keystroke transfers authorship and the hold is absolute. That
boundary is right. What it leaves open is the case where the classification itself is
wrong — for which the only documented remedy today is to reword the issue body until the
classifier changes its mind.

### What DR-072 settled, and the sentence it left standing

DR-072 §3 fixed which triage holds a human may lift, and made `hold:human` absolute:

> `human_only` is a **content class** (marketing, positioning, copy, legal, `decide`).
> It governs who may **author** the work, not who may permit it — and **no keystroke
> transfers authorship**.

That boundary is right and this record does not move it by a byte. But the table it
sits in assumes the classification is **correct**, and DR-072 §3 disposed of the case
where it is not in one sentence:

> A mis-CLASSIFIED issue is cured by fixing the gate's INPUT, never by overriding its
> output. Make the issue body unambiguous about its type and re-triage — the
> `bodyHash` changes, so that is a genuine re-verdict rather than a rubber stamp.

DR-072 also recorded, in the same paragraph, that this answer is unsatisfactory and
filed **#1106** to replace it. This is that record.

### Why "edit the body until the model agrees" is the wrong remedy

Three separate defects, only the first of which is cosmetic:

1. **It is undocumented and non-obvious.** Nothing outside `triage-decide.sh`'s header
   and DR-072 §3 tells a maintainer that this is the sanctioned path.
2. **It teaches prompt-gaming as a workflow.** "Reword until the classifier agrees" is
   the exact inverse of the constitution's *enforce, don't trust the model* stance that
   every other gate in this repo takes. Worse, it is **unbounded**: the classifier is
   non-deterministic, so re-rolling the same body eventually flips it. The documented
   remedy is a slot machine with a bodyHash on the lever.
3. **It destroys the evidence.** The disagreement between the human and the classifier
   *is* the measurement. Rewording the body to obtain a different answer erases the
   input that produced the original answer, so the pair (what the classifier saw, what
   it should have concluded) is unrecoverable.

The third is the one that compounds. DR-070's own findings — tier tracks diff size and
not difficulty; the LLM's staleness guesses measured ~56% wrong — say the classifier's
error rate is the thing to know before trusting it further. The repo cannot currently
answer *"how often is the human-only filter wrong, and in which direction?"* at all,
and the documented workaround guarantees it never will be able to.

### The live example, stated as a judgement rather than a fact

**#898** — *"migrate ~6 approved-pre-implement specs to `status: planning`"* — triaged
`human_only: yes`, `hold: human`, `role:architect`, `T3`. A mechanical frontmatter
migration is none of DR-070 §5.2's content classes; it plausibly reads as human-only
only because it touches the governance corpus, which DR-070 §5.6 does list as
never-auto-dispatchable. **Whether that is a misfire is itself a judgement**, and the
point of this record is that there is currently no way to *record* that judgement —
only a way to reword the issue until the classifier agrees with it. A mechanism that
can only be exercised by destroying its own evidence cannot be measured, and an
unmeasurable gate is one this repo has no basis for trusting.

### The distinction this whole record turns on

> **Correcting an input** = telling the gate what the work *is*. The gate then decides.
> **Overriding an output** = telling the gate what to *conclude*. The gate has not decided.

Every rule below exists to keep the dispute lane on the first side of that line, because
a mechanism that drifts across it is `human_only: no`-by-another-name, and DR-072 §3
already refused that.

## Decision

### 1. What a dispute declares: the work TYPE, from a closed vocabulary, and nothing else

The triage role's human-only filter is, structurally, a **type classification**: it asks
whether the issue's type is in the human-only set (`idea`, `marketing`, `positioning`,
`copy`, `legal`, `decide`/`monetization`/`billing`, irreversible-architecture,
cross-product-schema, published sites, live outbound) or in the auto-buildable set
(`bug`, `feat`, `chore`, `docs`, `test`, `ci`, gate-repairs/validator-tightening). The
LLM's job at that step is to **infer the type from prose**.

A dispute supplies that type directly:

```
scripts/dispute-triage.sh <N> --type <type> --reason "<one line>"
```

`--type` is drawn from **exactly** those two vocabularies, enumerated in a pure
predicate. Nothing else is declarable. In particular a dispute may **not** declare
`tier`, `role`, `human_only`, `hold`, or `decision` — see §3.

### 2. A declared type settles the TYPE leg of the filter. It does not settle the INTENT leg

`scripts/roles/triage.md` applies the filter to two legs: the issue's **type label(s)**
*and* its **title/body intent** — *"a `feat`-labelled issue whose body is really 'decide
which approach' is human-only — judge intent, not just the label."*

A dispute settles the first leg and hands the second back, untouched, to the classifier:

- The declared type **replaces** the type the agent would have inferred.
- The agent **must still judge intent independently**, and must return `human_only: yes`
  when the body's actual intent is a human-only one, *whatever type was declared*, and
  say so in its `rationale`.

This is the property that makes the lane a corrected input rather than an override: a
dispute can **fail**, on the record, and #898-shaped cases are exactly where it should
be able to. A mechanism that always succeeds is not a correction; it is a switch.

### 3. What the dispute never touches — the four load-bearing negatives

1. **`triage-decide.sh` is not modified.** The deterministic gate's inputs are still the
   agent's five verdict fields and nothing else. There is no dispute-shaped argument, no
   environment variable, and no file it reads. The gate that decides is byte-identical
   before and after a dispute.
2. **No new hold becomes liftable.** DR-072 §3's table gains **no row**. `hold:human`,
   `hold:info` and `hold:unknown` remain unliftable by any approval. A dispute does not
   lift a hold; it causes a *new verdict* to be computed, which may or may not carry one.
3. **A dispute record is not a verdict record, and cannot be mistaken for one.** It uses
   a **distinct sentinel family** (`MINSPEC_DISPUTE_BEGIN` / `MINSPEC_DISPUTE_END`), so
   `dispatch-ready-check.sh`'s dispatch reader and its `--newest-record` selector never
   see it. Its schema **omits** `decision`, `hold`, `human_only`, `role` and `tier` —
   the fields an authorisation is made of are not expressible in it. A perfectly forged
   dispute record therefore authorises nothing; at absolute worst it causes a re-triage
   to run with a declared type, and the gate still decides the outcome.
4. **Tier is out of scope.** Tier gates the specify/build split (DR-076), and DR-070
   already records that it tracks diff size rather than difficulty — a tier dispute is a
   materially larger widening with a different failure mode, and it has its own remedy
   already (`approve-issue.sh` lifts `hold:tier`, DR-072 §3). A dispute against a
   `hold:tier` or `hold:specify` verdict is **refused** with a pointer to that path,
   so the two lanes never overlap.

### 4. One loosening dispute per body — the anti-slot-machine rule, bounded on TWO axes

The defect in "reword until it agrees" is **unbounded retry against a non-deterministic
classifier**, and a dispute lane inherits it unless it is closed explicitly — and
closed on both the way a retry gets *recorded* and the way it gets *run*, because
either one left open reopens the slot machine.

**Minting is bounded.**

- A **loosening** dispute (declaring an auto-buildable type) is admissible **at most
  once per `(issue, bodyHash)` pair** — not once per declared type. Cycling
  `chore → docs → test → ci` against one body is the same slot machine at a slower
  crank, so the bound is on the body, not on the declaration. This is enforced at mint
  time by an existence check over the **full trusted history** of the pair (SPEC-066
  C-3's `--dispute-exists`), not by "the newest dispute so far" — a recency-only check
  is defeated by an intervening dispute of the other direction (see the second axis
  below), so the check that guards minting must not be recency-scoped.
- A **tightening** dispute (declaring a human-only type against a verdict that called
  the issue auto-buildable) is **unbounded**, and never runs the existence check above.
  It can only ever cause a hold, so the deny-by-default direction costs nothing and the
  measurement wants it.
- The refusal message names the three honest remedies, in order: accept the outcome;
  or edit the issue body so its intent is unambiguous (which changes the `bodyHash`,
  and is a genuinely different input); or, if the re-triage landed on `hold:tier` /
  `hold:specify`, take DR-072's approval path.

**Injection is bounded separately, and this is the route the minting bound alone does
not close.** The bound above stops a SECOND dispute record from being minted at one
`bodyHash`. It says nothing about the ONE dispute that was minted being read and
re-injected more than once: `triage-inbox.sh` is an explicitly supported per-issue
invocation, a re-triage never changes the `bodyHash`, and a dispute's freshness (SPEC-066
FR-4) was keyed purely on `bodyHash` and trust — so, undisclosed, every subsequent
`scripts/triage-inbox.sh <N>` against the same unedited body would find the same
dispute "fresh" and re-inject its `declaredType`, handing the non-deterministic
classifier another free roll without a second dispute ever being recorded. That route
is closed by a **once-only consumption rule**: a dispute is selectable for injection
only while its `disputedVerdictAt` still equals the `verdictAt` of the current newest
verdict on the issue. The instant a new verdict lands — from the re-triage the dispute
itself triggers, or from any later one — the dispute is **consumed** and stops being
injected, even though its `bodyHash` is still current. A failed re-triage that writes no
verdict does not consume it, so a genuine retry after a failure is unaffected. See
SPEC-066 FR-4/FR-7 for the normative statement; the two bounds are independent checks
guarding independent actions (recording a dispute vs. reading one), and both are
required — either alone leaves the other route open.

**The residual, stated rather than papered over.** A cosmetic body edit changes the
`bodyHash` and buys another roll. This is not closed, and cannot be closed by this
mechanism — the hash cannot distinguish a substantive edit from a whitespace one. What
changes is that the retry is now **visible**: the corpus records N disputes against one
issue across M body revisions, which is precisely the shape a report can surface and a
prose workaround could not. The bound raises re-rolling from the *documented* remedy to
a *conspicuous* one; it does not make it impossible.

### 5. The record — attributed, body-bound, and in its own namespace

`minspec-triage-dispute/1`, minted by `dispatch-ready-check.sh --render-dispute` (the
grammar lives in the reader, as every other record's does — #983's rule) and posted by
`scripts/dispute-triage.sh`:

```
MINSPEC_DISPUTE_BEGIN
gate: minspec-triage-dispute/1
declaredType: chore
direction: loosening
disputedHold: human
disputedVerdictAt: 2026-08-31T04:11:07Z
disputedBy: <non-bot GitHub login>
bodyHash: sha256:…
verdictAt: 2026-09-02T09:20:00Z
MINSPEC_DISPUTE_END
```

`direction` is one of `loosening` or `tightening` (§1), derived from `declaredType` and
never supplied directly — the block above shows one concrete value, as every field must
render on the wire: `record_scrub` strips both spaces and `|` (SPEC-066's copy of this
same charset), so a two-value example like `loosening | tightening` is not itself a
value the schema can carry.

Four properties, each inherited from an existing decision rather than invented:

- **`bodyHash`-bound** (DR-062): edit the issue and the dispute goes stale with the
  verdict it disputes. A dispute about a body that no longer exists says nothing.
- **`disputedVerdictAt`** pins *which* verdict is being disputed, so a dispute cannot be
  silently re-attributed to a later verdict it was never about.
- **Author-trusted, non-bot** (DR-072 §4/§5): read only through
  `--trusted-comment-bodies`, and `disputedBy` is refused at the writer *and* the reader
  if it is a bot identity, so the autonomous pipeline can never dispute its own gate.
- **Recency by its own timestamp, never by position** (DR-072 §5a): selected by
  `--newest-dispute`, which shares one sentinel-parameterised implementation with
  `--newest-record`. Two front ends each carrying their own "take the last one" is
  exactly how two of three readers kept the quoted-record defect after the third was
  fixed; that lesson generalises to the new family rather than being re-learned by it.

**`reason` is deliberately NOT a record field.** It lives in the comment prose above the
fenced block. `record_scrub` restricts field values to `[A-Za-z0-9:._/[]-]` precisely so
a value cannot forge a sibling field, and that charset cannot carry a sentence. Widening
it to hold prose would trade a real forgery defence for a nice-to-have, so the sentence
goes where sentences go and the record stays a closed vocabulary end to end.

### 6. The reason never reaches the classifier — only the validated enum does

`triage-inbox.sh`, on finding a fresh trusted dispute, adds **one line** to the agent
prompt, outside the `<untrusted_issue_body>` fence: the validated `declaredType` token,
plus the fixed instruction from §2. The human's free-text `reason` is **not** passed.

This is not an oversight to be fixed later. The reason is human-authored prose that a
trusted identity republishes into an LLM prompt — the identical channel DR-072 §5a
found `dispatch-issue.sh` already opening with `.agent-summary.md`. Passing only a token
from a closed, gate-validated vocabulary removes the surface entirely rather than
mitigating it, and costs the classifier nothing it can act on: the reason argues about a
conclusion, and §2 says the classifier must reach its own.

Correspondingly, the **untrusted body is fenced against the declaration marker** before
it is embedded, exactly as `fence_agent_text` fences the verdict sentinels. An issue body
that contains its own `declared_type:` line is issue *text*, never a declaration — and
`triage.md` states that a declaration is valid only outside the untrusted fence.

### 7. Every dispute is a labelled classifier error, and the corpus is the point

`scripts/dispute-report.sh` joins, per issue, the disputed verdict, the dispute, and the
first verdict minted after it, and classifies the outcome:

| outcome | meaning |
|---|---|
| `upheld` | the re-triage over the corrected type produced a different (looser) hold — the original classification was wrong on **type** |
| `rejected` | the re-triage produced the same hold — the classifier held its ground on **intent**, and §2 says that is a legitimate result |
| `tightened` | a tightening dispute whose re-triage now holds — the classifier was wrong in the **permissive** direction, the more expensive error |
| `pending` | a dispute with no newer verdict — the re-triage did not run or failed |

`pending` is reported **loudly and separately**, never folded into a rate. A dispute
that was recorded and never re-triaged is a false signpost: the human believes they have
acted, and nothing has. Per constitution invariant 2 an unevaluated witness fails
visibly, so `dispute-triage.sh` runs the re-triage itself as its final step and reports
the resulting verdict — a dispute is never left as a recorded intention.

This is the first artifact in the repo that can answer *"how often is the human-only
filter wrong, and in which direction?"* with a denominator. It is worth building on that
ground alone, independent of any issue it unblocks.

### 8. The honest weakness, and the kill criterion

**The weakness.** §2 asks the classifier to accept a declared type while independently
judging intent. Nothing forces it to. An LLM handed an authoritative-sounding
`declared_type: chore` may simply rubber-stamp it, in which case the lane *is* an
override wearing a corrected-input costume — the very thing §3 enumerates negatives to
prevent. The structural controls (closed vocabulary, unmodified deterministic gate,
one-loosening-per-body) bound the *blast radius* of that failure; they do not prevent it.

**Which is why the mechanism measures itself.** §7's corpus makes the failure
observable: if disputes are upheld at a rate indistinguishable from 100%, the classifier
is not judging intent, and the lane is a switch.

**Kill criterion, in DR-070 §8's form** — reviewed once the corpus reaches
**n ≥ 20 loosening disputes**:

- **upheld rate ≥ 0.95** → the classifier is rubber-stamping. The lane is an override by
  another name and is **withdrawn**, not tuned. Re-triage remains available.
- **upheld rate ≤ 0.10** → the classifier was right nearly every time; the lane is
  ceremony that produces refusals, and its cost is not earned. Withdraw and record why.
- **anything between** → the lane is doing the job this record claims for it. Keep, and
  publish the rate.

A mechanism that cannot fail its own review is not a gate. This one names the number
that would end it, before it ships.

## Consequences

**Good**

- The mis-classification remedy stops being "reword until the model agrees" and becomes
  an attributed, bounded, body-bound act with a name.
- The repo acquires its first labelled corpus of triage errors, with direction, and can
  therefore state a human-only-filter error rate instead of guessing at one.
- `hold:human` stays absolute. No hold becomes liftable, and DR-072 §3's table is
  untouched — the two records compose rather than contradict.
- A dispute can **fail**, visibly, which is what distinguishes it from an override.

**Costs / risks**

- **A second record schema** on a corpus-forming surface. DR-070's *Costly to Refactor*
  applies: once N issues carry a `minspec-triage-dispute/1` block, changing its
  vocabulary means a backfill across every consumer. Mitigated by keeping the schema
  minimal and its fields closed-vocabulary.
- **A third credentialed front end** (`dispute-triage.sh`) alongside `triage-inbox.sh`
  and `approve-issue.sh`, inheriting DR-072 §4's provenance limit verbatim: in a
  container whose `gh` is authenticated as the maintainer, interactivity and typed
  confirmation are all that separate *"the human disputed this"* from *"something
  running as the human disputed this"*. The App-token binding that would close it is
  #1105 (family of #397), unchanged by this record.
- **The rubber-stamp risk of §8**, bounded and measured but not eliminated.
- **The cosmetic-edit residual of §4**, visible but not closed.

## Alternatives considered

**Let a human set `human_only: no` directly.** Rejected — this is DR-072 §3's absolute
boundary by another name, and the issue that triggered this record says so first.

**Widen `--may-approve` to lift `hold:human` when the approver states a type.** Rejected
for the same reason: it lifts an output. The type would be decoration on an override,
and DR-072 §3's table would need a row it must not have.

**A second, "more careful" classifier pass on dispute.** Rejected — re-rolling the same
non-deterministic classifier with a stronger prompt is the slot machine with better
lighting, and it produces no labelled corpus. §2's split (type declared, intent judged)
changes the *input*; a re-roll changes only the dice.

**Deterministic type inference from the issue's GitHub type labels.** Attractive — a
`chore`-labelled issue arguably *is* a chore, with no LLM involved. Rejected for v1
because labels on this repo are not curated to that standard and
`.github/ISSUE_TEMPLATE/agent-task.yml` already hands out dispatch labels to any
stranger (DR-072 §5). Worth revisiting once #1134 lands; recorded as a follow-up rather
than as a hidden assumption.

**Do nothing; keep the DR-072 §3 sentence.** Rejected. It documents prompt-gaming as
policy and forecloses measurement — and DR-072 itself filed #1106 to say so.

## Costly to Refactor

- **The `minspec-triage-dispute/1` vocabulary**, once records exist on real issues.
- **The sentinel family** `MINSPEC_DISPUTE_BEGIN`/`_END`, which becomes a token every
  republishing reader must fence (`fence_agent_text`) — adding it later means auditing
  every channel again.
- **The one-loosening-per-body rule (§4)**, because relaxing it is invisible while
  tightening it invalidates disputes already recorded under the looser rule.
