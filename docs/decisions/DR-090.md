# DR-090: A harness refresh may only move a project forward

> **Born `proposed` per DR-029** — acceptance is a separate human act
> (*MinSpec: Accept ADR*). This record's live status is its frontmatter `status:`
> field, not this note.

## Context

*MinSpec: Refresh Harness Files* writes the harness templates **baked into the running
bundle**. #1095 established that this is not merely "as current as the last package
build" — it is actively destructive. In `AIClarityAU/sealbox`, a refresh run from
`aiclarity.minspec-0.1.24` (installed 2026-07-27, predating #1041/#1057/#1073) rewrote
three managed files to **older** content, deleting the *Coverage DISCLOSURE
(no-silent-gate)* block from `ai-review.yml` — the block that exists so a reduced review
panel cannot produce a verdict indistinguishable from a full-panel one. A refresh removed
a no-silent-gate feature, silently. That is constitution invariant 2 being deleted by the
tool that is supposed to install it.

Four properties of the current code turn "stale" into "destructive". Each is cited
because the fix has to change a specific one:

1. **A stale build does not skip; it writes.** For a Markdown harness section the merge
   ends at `merge-refresh.ts:953-957` — a section "proven unmodified against the recorded
   baseline" takes *whatever the running bundle renders*. For a managed region there is
   no baseline consulted at all: `scaffold.ts:952-957` splices the running bundle's block
   in whenever the bytes differ. Both branches are direction-blind; "differs" is not
   "older".
2. **The only identity that could have flagged it never moved.** The extension version
   was `0.1.24` before and after all three merges. No human and no tool comparing version
   strings could have caught it, and a same-version reinstall is itself unreliable.
3. **The one real fingerprint is machine-local and unordered.** `.minspec/template-baseline.json`
   (`merge-refresh.ts:1334-1373`) holds a per-section hash of the raw templates, but it is
   declared machine-local and untracked (`scaffold.ts:274-275`, with `git rm --cached` at
   `scaffold.ts:352`), so it does not exist in a fresh clone and never travels between
   machines — and `hasHarnessDrift` (`auto-bootstrap.ts:103-121`) compares it with `!==`,
   so it can say *differs*, never *older*. It even reads a downgrade as "templates
   updated — refresh now?" (`auto-bootstrap.ts:488-489`).
4. **The refresh then silences its own alarm.** `refreshHarnessFiles` ends by re-recording
   the running bundle's template hashes as the project's baseline (`scaffold.ts:1584`), so
   after a stale refresh the drift signal reads false. The reversion is not just silent at
   the moment it happens; it stays silent afterwards.

**Why authorship cannot answer this.** DR-089 taught the manifest to answer *whose bytes
are these?* — and it answers correctly here: the reverted `ai-review.yml` region **was**
MinSpec's own output. Being MinSpec's output is exactly why it was overwritten. #1095 is
an orthogonal question the refresh has never asked: *is what I am about to write newer
than what is already there?* Authorship establishes the right to write; it does not
establish the direction of the write.

**Blast radius.** SPEC-058 measured roughly ten harness-refresh commits per repo per 60
days across `scroogellm` and `sealbox` — so this path fires about weekly, per consuming
repo. And the downstream `minspec-ci-parity` job (present in sealbox; **not** produced by
this repo — repo-wide grep finds it only in prose at
`specs/minspec/SPEC-033-repo-governance-provisioning/requirements.md:28` and
`specs/minspec/SPEC-063-clean-uninstall/requirements.md:49`) emits *"run MinSpec: Refresh
Harness Files to re-sync"* as its remedy. A remedy that causes the fault it repairs is a
DR-003 false signpost with a machine-driven loop attached.

## Decision

### 1. Direction is a question the refresh must ask, before it writes

Every write path that replaces existing MinSpec-owned content — the Markdown
section-merge branch at `merge-refresh.ts:953-963` and the managed-region splice at
`scaffold.ts:952-957` — is gated on a **direction verdict** in addition to the DR-089
authorship verdict. Authorship stops being sufficient authority to write.

Two write paths are deliberately **not** gated, because neither can move a project
backwards: creating a file that does not exist (`scaffold.ts:1549-1552`, `:926-930`) and
appending a heading absent from disk (`merge-refresh.ts:959-963`). First adoption and
first scaffold are unaffected by everything below.

### 2. The ordered identity is a content-derived, gate-enforced template epoch

The bundle carries `TEMPLATE_EPOCH` — a monotone integer — plus `TEMPLATE_EPOCH_DIGEST`,
a digest over the whole rendered template corpus (the corpus `computeTemplateBaseline()`
already walks, `template-registry.ts:793-812`, which covers both `TEMPLATES` and
`MANAGED_REGION_TEMPLATES`). Both are ordinary source constants, baked in like any other
template byte; no new build-time injection is required.

The epoch is load-bearing only because a gate makes it move:

- **`npm run validate` recomputes the corpus digest** and fails when it disagrees with
  the recorded `TEMPLATE_EPOCH_DIGEST`, with the remedy "templates changed — bump
  `TEMPLATE_EPOCH` and re-record the digest". This is the missing gate #1095 names: today
  *nothing* asserts that the bundled template set is identified by anything that changes
  when the set changes.
- **The same check runs in CI**, not only in the local hook. Constitution invariant 2
  forbids a required check that one permission or config gap can disable, and
  `core.hooksPath` is exactly such a gap. Two witnesses, one rule, one implementation
  called from both surfaces (the Rule 12 / Goal G-6 pattern, `validate-frontmatter.ts:522-557`).
- **A duplicate epoch is refused at merge**, modelled on the existing
  `.github/workflows/dr-id-collision.yml`: two branches that both bump 41→42 would
  otherwise produce two different template corpora claiming one position in the order.

### 3. The record travels with the repo, so it is committed

`.minspec/harness-provenance.json`, **tracked** — not added to `MINSPEC_GITIGNORE_ENTRIES`:

```json
{ "templateEpoch": 42, "writtenBy": { "version": "0.1.24", "buildSha": "a1b2c3d" }, "writtenAt": "2026-09-06T00:00:00Z" }
```

`templateEpoch` is the only load-bearing field; the rest is diagnostic, for the human
reading the refusal message. It is written by every refresh that actually wrote managed
content, and by initial scaffold.

**This is a deliberate departure from DR-089's rejected "commit the manifest", and the
difference has to be stated or the two records read as contradictory.** DR-089 rejected
committing `.minspec/generated-hashes.json` on two grounds, and neither transfers:

- *"changes on every refresh, so it conflicts on any branch that also refreshed"* — the
  manifest is per-section and moves whenever any file moves. This record has one
  load-bearing field that changes **only when the template corpus changes**, i.e. at most
  once per template release, not once per refresh.
- *"the baseline is local state"* — true of the authorship question, which is answerable
  from the working tree. The direction question is not: sealbox's reversion happened
  **because** the only fingerprint was machine-local, so a second machine, a fresh clone,
  and CI each had nothing to compare against. A record that does not travel cannot answer
  a question about what another machine already had.

### 4. Four verdicts, and two of them hold the write

| Bundle epoch vs record | Verdict | Action |
|---|---|---|
| `build > repo` | **ahead** | Write as today (still subject to DR-089 authorship), then stamp the new epoch |
| `build == repo` | **level** | Write as today (a no-op in practice), record unchanged |
| `build < repo` | **behind** | Write nothing that would change managed content. Report every held path, name both epochs, and say the actionable thing: *update MinSpec*. Leave the record untouched |
| record absent, unparseable, or carrying an epoch this bundle cannot read | **unknown** | Fail closed exactly as *behind*, with a distinct message and an explicit one-shot override |

The bundle's own epoch is a source constant, so a bundle that *runs* this gate always has
one; "the bundle has no epoch" is not a fourth verdict but the pre-feature bundle, covered
under Consequences.

*Unknown* fails closed for DR-089 §2's reason — absence of evidence is not evidence of
absence, and the fail-open direction is the one that destroyed data. It is also the
migration state of every repo that exists today, which is why it gets an override the
*behind* verdict does not: a human confirmation that lists exactly which files would
change. The override is offered **only** by the interactive command. The auto-bootstrap
refresh trigger (`auto-bootstrap.ts:482-497`) never takes it — it reports and stops,
because an override taken by a background prompt is not a human act.

### 5. A held refresh must not re-stamp the drift baseline

`scaffold.ts:1584` currently re-records the running bundle's hashes unconditionally at the
end of every refresh. When any path was held, that write records *"in sync with this
bundle"* — a false negative that hides the hold from every later signal, which is the
property that made the sealbox reversion stay invisible after the fact (Context §4). Under
a hold the baseline is left untouched for the held entries. The hold stays observable until
it is resolved, per constitution invariant 2.

### 6. What a refusal costs, stated plainly

A genuinely-newer bundle refuses to update a repo whose record is absent until a human
overrides once, and refuses outright while the repo's record is ahead. That is the
intended trade: the tool declines to act rather than act in the wrong direction. It is
bounded — the override is one confirmation per repo, ever, and the *behind* refusal is
resolved by updating the extension, which is the thing that was actually wrong.

## Alternatives rejected

- **Fetch canonical templates at refresh time.** Contradicts constitution invariant 1
  (core functionality works offline, no network without explicit consent) and the Tier-0
  posture (DR-004). Worse than the invariant violation: it would make the *correctness* of
  a refresh depend on connectivity, so an offline user gets a wrong answer rather than a
  degraded one — the precise property Tier-0 exists to deny. An opt-in "check whether
  newer templates exist" is a different feature with its own consent surface and is not
  decided here (follow-up below).
- **Order by build timestamp** (the SPEC-060 FR-1 stamp). Monotone by construction, so it
  can never be forgotten to move — genuinely simpler. Rejected because it orders by
  wall-clock rather than by content lineage: a bundle packaged *today* from a branch that
  predates three merged template changes claims to be newer than the content it is
  missing, which is the exact sealbox shape. The timestamp is still carried in the record
  as a diagnostic, just not as the ordering key.
- **Order by extension version string.** This is the signal that already failed — `0.1.24`
  before and after three template merges (#1095). A version bump is a publisher habit, not
  a gate.
- **Derive direction from the consuming repo's git history.** DR-089 already rejected the
  git-history variant for the manifest — squash merges and shallow clones break it — and
  the refresh must work in a directory that is not a git repo at all.
- **Warn loudly but still write** (issue option 1 without option 2). A warning followed by
  the destructive write is DR-089's fail-open direction with better manners. The warning's
  audience here is partly a CI parity job, which does not read prose.
- **Refuse only on a net deletion inside a managed region.** Catches the sealbox case
  without any provenance mechanism, and was tempting for exactly that reason. Rejected: it
  is a heuristic over content, so a legitimate template update that removes a line is
  indistinguishable from a reversion — it would both false-positive on real updates and
  miss a same-length backwards rewrite.

## Consequences

**Accepted cost.** Every existing adopter's next refresh holds and asks once. Some will
read that as a regression in a tool that used to "just work"; it is the tool declining to
guess, and the alternative is what #1095 documents.

**This ships a new file into every adopter's `.minspec/`, and that part cannot be undone**
— the same class of commitment DR-089 §3 made with `hashVersion`. A later format change
must decide explicitly what to do with v1 records, and `SPEC-063`'s uninstall inventory
gains a row.

**A residual hole is accepted, not closed.** A bundle deliberately packaged from an
unmerged branch that bumped the epoch past main's will still be ordered ahead and will
still write. The collision gate (§2) catches it when that branch merges, not before. The
mitigation is that packaging an unmerged branch is a visible publisher act, not an
accident of staleness.

**Rollback behaviour is designed but unverified.** An older bundle meeting a
`.minspec/harness-provenance.json` it does not understand simply ignores the file and
behaves as today — i.e. it can still revert the repo. There is no way to make an old
bundle honour a record it predates; this is stated so nobody reads §3 as protecting a
project from bundles built before it. It needs a real test once §1–§4 exist.
